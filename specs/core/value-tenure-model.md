# VCDesign Tenure Model: 点の責任と線の責任

## Status

**Design principle / Reading aid — not authority.**

このドキュメントは、VCDesign が守る責任を
**点の責任（Gate）**と**線の責任（Tenure）**に区別し、
VCDesign の主戦場が後者であることを明文化する設計原則である。

仕様上の権威は `core.yaml` / `policies.yaml` / `metrics.yaml` にある。
本文書で導入する概念の規範的な実体は
`schema_case.yaml`（tenure フィールド群）と `metrics.yaml`（tenure_metrics）にあり、
本文書はその読み方を固定する。

既存文書との役割分担:

- `ai-adaptive-loop-model.md` — 4ループで**現実運用の構造**を読む文書
- `agent-era-model.md` — Agent 時代の**外部説明フレーム**を整理する文書
- `value-tenure-model.md`（本文書）— 責任の**時間軸上の性質**（点か線か）を定義し、将来の編集で VCDesign の差別化が薄まらないよう錨を打つ文書

---

## 1. なぜこの区別が必要か

2026 年時点で、業界の議論は「AI に作らせて、人間が責任を持つ」に収束しつつある。
そこで語られる「責任」は、ほぼすべて**承認の一点**に錨を下ろしている。

```text
問題定義 -> 委任 -> 検証 -> 最終承認   ← ここが「責任」と呼ばれる
```

これは実在する責任であり、VCDesign も Judgment Closure / IDG / 実行ゲートとして
既に構造化している（A2: Judgment Closure Precedes Action）。

しかし、この語り方には空白がある。
**作った直後の責任**は語られるが、
**価値を継続させるために責任を負い続けること**は語られない。

- 承認した人が異動・退職した後、その判断は誰のものか
- 誰も見ていない自律運用中に起きた価値のドリフトは、いま誰の責任か
- 後任は、どの根拠からその判断を再導出できるのか

レガシーシステムとは、技術的に古いシステムのことではない。
**責任の所在が拡散したまま継続しているシステム**のことである。

---

## 2. 定義: Gate と Tenure

| 観点 | 点の責任（Gate） | 線の責任（Tenure） |
|------|-----------------|-------------------|
| 問い | 「今、これは正しいか？」 | 「誰がこれを持ち続け、時間と交代を生き延びるか？」 |
| 時点 | 承認の瞬間 | 承認後の全期間 |
| 主体 | その場の final_decider | 現在の owner と、その継承の連鎖 |
| 消え方 | 承認の省略・形骸化 | 保有者の離脱・再確認の停止・根拠の散逸 |
| 既存の対応 | Judgment Closure / IDG / 実行ゲート | **本モデルが対象とする空白** |
| 業界の状況 | 検証・品質保証として急速にコモディティ化 | ほぼ未着手 |

**Gate は Tenure の開始点であって、Tenure の代替ではない。**
承認済みであることは、現在も責任が保有されていることを意味しない。

---

## 3. 反転: 自律化は Tenure を不要にせず、必要にする

直観に反するが、これが本モデルの中心命題である。

自律運用が進むほど、人はループの外に出る。
人がループの外に出るほど、
「誰も見ていない間に起きたドリフトの責任は、いま誰にあるのか」
という問いは消えるのではなく**鋭くなる**。

- 監視（オブザーバビリティ）は「システムが健全か」を答える
- 承認ゲートは「この変更は正しかったか」を答える
- どちらも「**この価値をいま誰が保有しているか**」には答えない

したがって、自律運用の普及は VCDesign の前提を弱めるのではなく、
VCDesign が必要になる条件そのものである。

---

## 4. 差別化の死守事項

VCDesign Tenure Model は以下を複製しない。
将来の編集でこの区別が薄まった場合、それは仕様の劣化である。

| 既存の規律 | 記録するもの | 追わないもの |
|-----------|------------|------------|
| ADR（Architecture Decision Record） | 決定の凍結記録 | 決定後の責任の移り変わり |
| SRE / オブザーバビリティ | 運用の健全性 | 誰が責任を保有しているか |
| 承認ワークフロー | 承認の事実 | 承認者離脱後の再導出可能性 |
| RACI / ITIL 変更管理 / ISO 27001 統制オーナー管理 | 現在の責任者の**名義** | 後任が判断を**再導出できるか** |

注意すべきは 4 行目である。
「いま誰が責任を保有しているか」を名指しすること自体は新しくない。
RACI も ITIL も統制オーナー管理も既にそれをやっており、
owner の空白なら `owner_missing`（metrics.yaml）で足りる。

VCDesign 固有の対象は、名義ではなく「**判断の再導出可能性の継承**」である。

- 「オーナーとして名前が載っている」ことと、「なぜその判断をしたかを後任が再導出できる」ことは別物である
- 前者は既存の統制が扱う。後者だけが VCDesign 固有であり、`re_derivation_basis` と custody_chain の `re_derivation_confirmed` がその実装である

したがって custody_chain が追うのは名義の変遷ではなく、
**再導出可能性が交代をまたいで確認され続けたか**の記録である。
これが唯一の差別化点である。

## 5. Tenure を構成する 5 フィールド

規範的な定義は `schema_case.yaml`（version 0.2 以降）にある。
各フィールドは、それぞれ特定の Tenure 崩壊モードを防ぐ。

| フィールド | 防ぐ崩壊モード |
|-----------|--------------|
| `value_intent` | 基準線の喪失。生かし続けたい価値が書かれていなければ、ドリフト（価値からのズレ）はそもそも定義できない |
| `custody_chain` | 継承の断絶。責任の引き渡しが記録されなければ、A1（責任非消失）は交代をまたいで検証不能になる |
| `re_derivation_basis` | 根拠の散逸。後任が判断を再導出できなければ、責任は名目上の保有に堕ちる |
| `review_triggers` | 見直しの形骸化。カレンダー駆動のレビューは儀式化する。見直しは**事象・条件駆動**で定義する |
| `last_reaffirmed` | 保有の減衰。Tenure は放置で減衰する。「今も有効」と誰かが確認した時刻を持たない責任は、保有されているとは言えない |

`next_review_at`（既存フィールド）と `review_triggers` の関係:
`next_review_at` は「いつ見るか」、`review_triggers` は「何が変われば見るべきか」。
Tenure の観点では後者が主であり、前者は補助である。

**減衰の扱い（設計判断・2026-07）:**
`last_reaffirmed` の時間経過による減衰は**弱いシグナル（observation / INFO）**であり、
warning 以上には扱わない。再確認の義務は事象駆動であり、
**custody 交代時と review_trigger 発火時に必須**となる。
時間減衰を warning にすると、それを消すための定期打刻が生まれ、
review_triggers で退けたカレンダー儀式が reaffirmation に移るだけだからである。
なお両者は軸が異なる — review_triggers は「決定の正しさを世界の変化に照らして見直すべきか」、
last_reaffirmed は「保有（custody・注意）がまだ生きているか」— が、
強制の仕方を誤るとどちらも同じ儀式化に合流する。
何年も正当に安定する決定（例: 物理制御系の安全境界）に固定閾値の warning を
出し続けてはならない。将来の編集者はこの減衰を「レビュー義務」に変えないこと。

## 6. 既存仕様との接続

本モデルは新しい公理を導入しない。既存の権威の時間軸方向への展開である。

- **A1（責任非消失）**: A1 は「責任は移転・エスカレーション・解放されてよいが、静かに無所有になってはならない」と定める。custody_chain はこの「移転」を検証可能な構造にしたものである。
- **temporal-governance.md（append-only 責任トレース）**: 責任の引き渡しと再確認は、上書きではなく追記される責任イベントである。custody_chain は append-only である。
- **metrics.yaml / owner_missing**: 「いま owner がいない」ことは既に検知できる。tenure_metrics はこれを補完し、「owner はいるが保有が減衰している」「引き渡しが記録されずに交代した」を検知する。
- **schema_case.yaml / owner, final_decider**: 既存の責任モデルはそのまま維持される。tenure フィールドはすべて optional として追加され、既存の適合性を壊さない。

---

## 7. スコープの歯止め

- **AI 専用ガバナンスに狭めない。** 曖昧な指示を受けた人間にも境界侵犯は起きる。Tenure の崩壊は人間の担当交代でも AI の自律運用でも同じ構造で起きる。本モデルの実例（`../examples/custody-handover.md`）が人間の交代を扱うのはこのためである。
- **承認ゲートの作り込みに寄せない。** 検証・品質保証は既に混雑した領域であり、コモディティ化する。VCDesign は Tenure 側に賭ける。
- **過大な機能追加をしない。** Tenure の痛みはインシデントが積み上がるまで市場には見えない。したがって本モデルの当面の性格は、思考リーダーシップ・内部運用・タイムスタンプ付き記録であり、売り物への最適化ではなく概念の明晰さを優先する。

---

## 8. 検出の問い（Detection Questions)

運用中のシステムに対して、Tenure の状態を診断する問い:

1. この決定の `current owner` を、組織図ではなく記録から答えられるか。
2. 最初の決定者が明日去った場合、後任は何を読めば同じ判断を再導出できるか。
3. この決定が「見直されるべき状態」になったことに、カレンダー以外の何が気づくか。
4. 最後に誰かが「この決定は今も有効だ」と確認したのはいつか。
5. 過去 1 年の担当交代のうち、引き渡しが責任イベントとして記録されたものは何件か。

一つでも答えられない場合、その決定は Gate を通過しただけで、Tenure は保有されていない。
