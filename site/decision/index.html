判断

Δ を受けて、人間が6語のいずれかで閉じます。ほかの語彙は使いません。すべての判断は一つの判断ゲートを通ります。

規範：core.yaml の decision と closure_loop、policies.yaml の judgment_gate、enforcement、temporal_governance。記録の形：schema_log.yaml。

1. 判断は人間が閉じる

  • すべての判断の最終判断者（final_decider）は人間です。AI が案件について出したものは、人間が判断を閉じるまで提案です（公理 A3）。
  • 閉じた判断は、その宣言を通じて実行してよい範囲を許可します。人間が閉じた判断で許可された範囲を越える実行は行いません。範囲の内側での実行には、改めての判断は要りません。範囲を越える変化は Δ として観測し、判断し直します（公理 A2）。
  • 境界での判定（pass / deny / unknown）は、一回ごとの越境の検査で、判断ではありません。unknown は止めて上げ、pass として扱いません。

2. 6語

6語は正本の Decision をそのまま使います。VCDesign では、それぞれを宣言の扱いと次の状態に対応させます（implementation.md §3）。

判断意味宣言の扱い次の状態
Proceed現在の構造・現在の宣言のまま進める現在の宣言を維持する。章を替えない修正を含むactive
Expand観測された Positive Δ に基づき、対象・規模・接続を広げるblast_radius を広げる（before / after）。Positive Δ の観測と復旧能力の確認が必須active
Limit価値はあるが伝播範囲が広すぎるため、対象・権限・規模・期間を狭めるblast_radius を狭める（before / after）active
Reframe価値・対象・境界・前提を再定義する新しい章として前提・境界・責任者・宣言を定め直すreframed
Defer判断材料が揃うまで、責任付きで保留する暫定責任者と次回判断時刻を置くdeferred
Retire次の価値生成につながらないため終了する責任を解放し、残すものの保有者を移す。開始前の案件では開始しない判断を含むretired

確定した Δ は、判断で閉じるまで責任の下にあります。Defer は、責任者と見直しの時刻を付けて閉じる経路であり、逃げ道ではありません。

3. 判断ゲート

すべての判断は、この一つのゲートを通って人間が閉じます。確認項目は正本の Review Output（Upside / Downside / Continuity / Asymmetry / Decision）に従い、5原則の順に並びます。長期の判断か短期の判断かは確認の深さの違いで、別のゲートは設けません。

原則確認すること
残すvalue_intent が宣言されている。residual_assets が保有者付きで宣言されている
見つけるspread_signals.expected が宣言されている。Positive Δ が平均的な効果と分けて記録されている
閉じるblast_radius が宣言されている。共有される区画があれば failure_domain が宣言されている。上流の結論が確かめ直されている
試すreversibility が宣言されている。停止の経路が確認されている
伝える判断の根拠が記録されている。長く続く案件では再導出の根拠が記録されている

4. 判断ごとに必要なもの

判断必要なもの（judgment_gate.per_decision）
Proceed追加の項目なし（判断ゲートの確認は通る）
Expand観測された Positive Δ（spread_signals の observed または unexpected）／拡大後の範囲でも復旧できることの確認／blast_radius の before と after
Limitblast_radius を狭めた before と after
Reframe今の章が続けられないこと／新しい前提と境界／新しい責任者／構造に関わる場合は supervisor の承認
Defer保留の理由／暫定責任者／次回判断時刻（既定の上限は7日。超えたら supervisor が閉じさせる）
Retire隠れた依存がないこと／責任の解放／関連する章への通知／残すものの保有者の移転

5. Expand と Limit は宣言の更新

Expand と Limit は、章を替えずに blast_radius の宣言を更新する判断として、before と after を記録します。Expand は宣言を広げ、Limit は宣言を狭めます。

  • 宣言の更新を伴わない「小さな試行」は Limit ではありません。上限のない試行として判断ゲートで止めます。
  • 平均的な効果が出ただけでは、Expand の根拠になりません。

架空の部品工場での Expand の記録例です（point-vs-line-improvement.md より抜粋）。

decision:
  value: expand
  positive_delta_refs: [reuse_cost_decline, unsolicited_pull]
  declaration_update:
    before:
      scope: 1〜3 号ラインのデータ収集のみ（制御系には書き込まない）
      max_loss: {unit: hours_data_gap, value: 8}
    after:
      scope: 1〜4 号ラインのデータ収集と品質管理課への読み取り連携（制御系には書き込まない）
      max_loss: {unit: hours_data_gap, value: 8}
      approved_by: {role: plant_manager}
  decided_by: {role: plant_manager}

6. Positive Δ と Expand

「伝播可能にする」は、自動で広げることではありません。

  • Positive Δ の観測と、保有者を付けた保有は止めません。停止・隔離・blocking の流れにも入れません。
  • 実際に広げるのは Expand 判断です。Expand には、観測された Positive Δ と、拡大後も復旧できることの確認が要ります。
  • 前提が欠けているとき止まるのは Expand 判断の方で、観測や保有ではありません。
  • 原因が特定できない上振れは、境界の guard で unknown とし、拡大の根拠にしません。

7. 止める条件

判断ゲートは、Negative Δ の伝播と、前提を欠いた Expand 判断を止めます（judgment_gate.hard_stops）。Positive Δ の観測と保有は止めません。

  • 致命的な下振れ（責任者の有無によらない）
  • 責任者がいない
  • 人間の最終判断者がいない
  • 不可逆なのに最大損失が宣言されていない
  • 観測された Positive Δ のない Expand
  • 復旧能力を超える Expand

blocking は Negative Δ と Expand 判断にだけ使います。Positive Δ の観測や保有に関する指摘は、最大でも warning です（policies.yaml enforcement）。

8. 判断の記録

  • 判断ごとに、Upside / Downside / Continuity / Asymmetry の観点で根拠を残します（decision.basis）。根拠のない判断は、指標 decision_without_basis で捉えます。
  • システムの状態は巻き戻せますが、責任の記録は追記のみです。提案、判断と根拠、owner、当時の証拠、境界の判定、巻き戻しの理由は消しません。訂正は新しい記録を足して行い、前の記録を消しません（temporal_governance）。

9. 避けるパターン

  • 平均的な成功だけを理由にした Expand
  • 宣言のない試行（上限のない「実験」）
  • 責任者や見直しの時刻がない Defer
  • 生きている依存を隠したままの Retire
