Re-derivation Layer

再導出層 — ロボットの動作が"責任"に触れる場所

VCDesign を、物理AI／OT境界に降ろすと現れる層。新しい方法論ではなく、適用ケース。

自律ロボットが「P-102の点検、完了」と返す。信号としては正しい。だが—— 誰の権限でそれを"点検"と呼べるのか。どの根拠で"完了"と判断したのか。 そして半年後、別の担当が「なぜこの判断は妥当だったのか」を再構成できるのか。 動作は記録されている。意味と、その根拠は、どこにも無い。

スタックのどこが空いているか

ROS2 から設備へ出る変換は、実は二枚ある。通信・情報モデルの変換（A層）は、 ほぼ標準化された。OPC UA の Robotics Companion Spec は状態監視からタスク制御へ上がり、 搬送・フリートは VDA5050／Open-RMF が受ける。だが、動作を "運転責任と業務意味"へ変換する層（B層）には、まだ標準が無い。

再導出層とは

再導出層は、NavigateTo(x,y) を「P-102の点検」に、CaptureImage を 「警報A-17の現場確認」に変える層だ。ただし、意味の付け替えだけでは足りない。 誰の権限で・どの根拠で、そして後任が"なぜ"を再構成できるかを一緒に運ぶ。

この最後の一点を VCDesign は re_derivation_basis と呼ぶ。 所有者名（誰の担当か）を継承するのではなく、判断の根拠（なぜ妥当だったか）を継承する。 RACI でも ADR でも ISO の owner-tracking でも、ここは埋まらない。 ＝ VCDesign が RACI 等と分かれる核心が、そのまま B層 の中身になる。

なぜ今か

フィジカルAI の基盤モデルが現場へ降りてくると、ロボットは"動く"ようになる。 A層 は上へ伸び、B層 の縁に触れる。三方向——下（ロボットの companion spec）、 横（フリート標準）、上（MES / CMMS）——がこの縫い目に迫るが、どれも自分の側しか モデル化しない。中央の責任・意味は、誰のものにもならないまま残る。

最初に効くのはどこか

規制製造——医薬・化学・食品。自律ロボの点検・現場確認の結果がバッチ記録や コンプラ判断に流れる瞬間、その判断根拠の監査可能性が"法的に"要求される。 「あれば良い」ではなく「無いと通らない」に変わる。歯があるのはここだ。

これは製品ではない。標準化が及ぶ前に、この層に名前を付けて置いておくための記述。
